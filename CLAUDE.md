# Jellio TV

Android TV client for Jellio: a native Nuvio lookalike, backed entirely by a
Jellio-Plugin server (Jellyfin + Gelato) over its own real REST API. No local
media, no bundled catalog addon runtime; this app is a thin, directly
rendered TV client over a server that already does every real catalog
aggregation, search, and stream resolution job itself.

## Relationship to Jellio-Plugin

`NoahSKipp/Jellio-Plugin` is this app's own real backend: its `Controllers/`
already expose everything a client needs (System Info, Views, Items, Images,
Favorites/Watchlist, playback URLs, the Calendar, Group Watch chat) over
plain Jellyfin-compatible REST, the exact same surface `frontend/runtime/
api.js` already calls from the web build. This app calls that same real
surface from Kotlin instead of JS. No new server-side work should exist here
that Jellio-Plugin doesn't already expose; if a screen needs data the plugin
doesn't serve yet, that's a Jellio-Plugin change first, not a workaround
here.

Auth mirrors `frontend/runtime/auth.js`'s own real shape (a token store
independent of anything else, real Jellyfin `/Users/AuthenticateByName`
login), reimplemented over DataStore instead of localStorage.

## Architecture

```
app/src/main/java/com/jellio/tv/
  JellioTvApplication.kt   Hilt entry point
  MainActivity.kt          hosts the top pill nav + whichever screen is active
  ui/theme/                Color.kt/Type.kt/Theme.kt, mirrors css/app.css's
                            own :root tokens in Jellio-Plugin by hand
  ui/nav/                  TopNavPill.kt, the same floating pill
                            components/mobileNav.js renders on a phone,
                            anchored to the top of the screen instead of the
                            bottom (a D-pad's own "up" out of any row lands
                            here the same way a phone's own upward swipe
                            reaches the bottom pill)
  ui/home/                 one package per real screen, mirrors
                            Frontend/screens/ in Jellio-Plugin
```

Every screen mirrors its own real counterpart in Jellio-Plugin's
`Frontend/screens/`: same data, same real hierarchy, reworked for a
10-foot, D-pad-driven interface rather than a mouse/touch one. Design
tokens (color, radius, the trending accent) are the one real source of
truth in `css/app.css`; this app's own `ui/theme/Color.kt` copies the real
values by hand and stays in sync with it, not the other way around.

## Release automation

Mirrors Jellio-Plugin's own `Makefile`/`release.yml`: `workflow_dispatch`
runs `make release`, which bumps `versionName` in `app/build.gradle.kts`
with git-cliff off conventional commit history, tags, and creates a GitHub
release. `versionCode` is derived at build time from `GITHUB_RUN_NUMBER`,
not hand-bumped. `publish.yml` then builds a debug-signed APK (no release
keystore configured yet) and attaches it, plus checksums, to that release.
Needs the same `RELEASE_TOKEN` repo secret Jellio-Plugin already uses (a
PAT with `contents:write`; the default `GITHUB_TOKEN` cannot trigger
`publish.yml`'s own `release: released` event).
